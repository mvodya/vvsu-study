## Система контроля версий

Система контроля версий хранит историю изменений проекта и позволяет вернуться к предыдущему состоянию файлов

Git является распределенной системой контроля версий. Полная история проекта хранится в локальном репозитории, поэтому просматривать изменения и создавать коммиты можно без подключения к сети

Сохраненное состояние проекта называется коммитом. Коммит ссылается на снимок файлов проекта и предыдущие коммиты, содержит имя автора, дату и сообщение

## Установка и настройка

Проверить доступность Git можно командой

```bash
git --version
```

Перед первым коммитом нужно указать имя и адрес электронной почты автора

```bash
git config --global user.name "Student Name"
git config --global user.email "student@example.com"
```

Параметр `--global` применяет настройку ко всем репозиториям текущего пользователя

Основную ветку для новых репозиториев можно назвать `main`

```bash
git config --global init.defaultBranch main
```

Посмотреть действующие настройки можно командой

```bash
git config --list
```

## GitHub Desktop

[GitHub Desktop](https://desktop.github.com/) предоставляет графический интерфейс для основных операций Git

Через него можно создать или клонировать репозиторий, просмотреть изменения, выбрать файлы для коммита, создать ветку, выполнить слияние и обменяться изменениями с GitHub

Основные элементы интерфейса

| Элемент        | Назначение                                 |
| -------------- | ------------------------------------------ |
| Changes        | Измененные файлы и подготовка коммита      |
| History        | История коммитов текущей ветки             |
| Current branch | Переключение и создание веток              |
| Fetch origin   | Проверка изменений в удаленном репозитории |
| Pull origin    | Получение удаленных изменений              |
| Push origin    | Отправка локальных коммитов                |

Сообщение коммита вводится в поле `Summary`, после чего коммит создается кнопкой `Commit to BRANCH_NAME`

При конфликте GitHub Desktop показывает список конфликтующих файлов. Исправление выполняется в текстовом редакторе, после чего файл отмечается как разрешенный и создается коммит слияния

GitHub Desktop не заменяет сам Git. Репозиторий и коммиты имеют тот же формат, поэтому терминал и графический интерфейс можно использовать для одного проекта

## Репозиторий

Репозиторий содержит файлы проекта и историю их изменений

Команда `git init` создает репозиторий в текущем каталоге

```bash
mkdir demo-project
cd demo-project
git init
```

В каталоге появится служебная папка `.git`. Удаление этой папки удаляет локальную историю и настройки репозитория

Команда `git clone` загружает существующий удаленный репозиторий вместе с его историей

```bash
git clone https://github.com/USER_NAME/demo-project.git
```

Для нового локального проекта используется `git init`, для копирования существующего проекта используется `git clone`

## Состояния файлов

Git различает несколько состояний файла

| Состояние | Описание                                               |
| --------- | ------------------------------------------------------ |
| Untracked | Файл еще не добавлен в историю                         |
| Modified  | Отслеживаемый файл изменен после последнего коммита    |
| Staged    | Текущая версия файла подготовлена к следующему коммиту |
| Committed | Версия файла сохранена в локальной истории             |

Изменения проходят через три области

```text
Рабочий каталог -> Индекс -> Локальный репозиторий
```

Команда `git status` показывает текущую ветку и состояния файлов

```bash
git status
```

Команда `git add` помещает выбранное изменение в индекс

```bash
git add README.md
git add src/main.py
```

Добавить все изменения текущего каталога можно командой

```bash
git add .
```

Перед `git add .` следует проверить `git status`, чтобы не добавить временные файлы или данные, которые не должны попасть в репозиторий

## Просмотр изменений

Команда `git diff` показывает изменения рабочей области, которые еще не добавлены в индекс

```bash
git diff
```

Изменения в индексе просматриваются отдельно

```bash
git diff --staged
```

Команда `git restore` восстанавливает файл рабочего каталога из индекса и удаляет изменения, которые еще не добавлены через `git add`. Если файл не менялся в индексе, это будет версия из последнего коммита

```bash
git restore README.md
```

Убрать файл из индекса без удаления его изменений можно командой

```bash
git restore --staged README.md
```

## Коммиты

Команда `git commit` сохраняет подготовленные изменения в локальной истории

```bash
git commit -m "docs: add project description"
```

Сообщение должно кратко описывать выполненное изменение. Формулировки `update`, `changes` и `fix` без дополнительного пояснения не передают назначение коммита

В один коммит следует включать только связанные изменения. Добавление новой функции и исправление постороннего текста лучше сохранить разными коммитами

Краткая история выводится командой

```bash
git log --oneline
```

Историю всех локальных веток удобно просматривать в виде графа

```bash
git log --oneline --graph --all
```

Содержимое выбранного коммита показывает `git show`

```bash
git show COMMIT_HASH
```

## Ветки

Ветка является именованным указателем на коммит, который перемещается при создании новых коммитов в этой ветке. Она позволяет изменять проект отдельно от основной линии разработки

Список локальных веток выводится командой

```bash
git branch
```

Создать ветку и сразу переключиться на нее можно командой

```bash
git switch -c feature/readme
```

Переключение на существующую ветку выполняется без `-c`

```bash
git switch main
```

Команда `git merge` добавляет изменения указанной ветки в текущую. Перед слиянием нужно переключиться на ветку, которая должна получить изменения

```bash
git switch main
git merge feature/readme
```

После успешного слияния ненужную локальную ветку можно удалить

```bash
git branch -d feature/readme
```

## Конфликты слияния

Конфликт возникает, когда Git не может самостоятельно объединить несовместимые изменения одного участка файла

Git отмечает конфликтующий участок специальными строками

```text
<<<<<<< HEAD
Текст из текущей ветки
=======
Текст из присоединяемой ветки
>>>>>>> feature/readme
```

Для разрешения конфликта нужно отредактировать файл, оставить правильный вариант и удалить все служебные строки конфликта

Исправленный файл добавляется в индекс, после чего слияние завершается коммитом

```bash
git add README.md
git commit -m "merge: resolve README conflict"
```

Отменить незавершенное слияние можно командой

```bash
git merge --abort
```

## Удаленный репозиторий

Удаленный репозиторий используется для обмена изменениями и хранения доступной через сеть копии проекта

Git-хостинг предоставляет удаленные репозитории и веб-интерфейс для их просмотра. Наиболее распространены GitHub и GitLab, далее в примерах используется GitHub

Связь локального репозитория с удаленным добавляется командой

```bash
git remote add origin https://github.com/USER_NAME/demo-project.git
```

Проверить адреса удаленных репозиториев можно командой

```bash
git remote -v
```

Первая отправка ветки `main` выполняется командой

```bash
git push -u origin main
```

Параметр `-u` связывает локальную ветку с удаленной. Следующие изменения можно отправлять короткой командой

```bash
git push
```

Команда `git pull` получает изменения связанной удаленной ветки и объединяет их с текущей локальной веткой

```bash
git pull
```

GitHub не принимает пароль учетной записи при выполнении Git-команд через HTTPS. Для авторизации используется персональный токен, менеджер учетных данных или SSH-ключ

## Файл .gitignore

Файл `.gitignore` содержит шаблоны путей, которые Git не должен добавлять в репозиторий

Пример для проекта на Python

```gitignore
__pycache__/
*.pyc
.venv/
.idea/
.DS_Store
```

Каждый шаблон записывается на отдельной строке. Символ `*` заменяет любую последовательность символов

Правило не действует на файл, который уже отслеживается Git. Такой файл нужно сначала удалить из индекса командой `git rm --cached`, не удаляя его из рабочего каталога

```bash
git rm --cached settings.json
```

## Markdown

Markdown используется для оформления текстовых файлов с расширением `.md`

Заголовки обозначаются символами `#`

```markdown
# Заголовок первого уровня

## Заголовок второго уровня
```

Элементы маркированного списка начинаются с `-`

```markdown
- Первый пункт
- Второй пункт
```

Ссылка состоит из текста в квадратных скобках и адреса в круглых скобках

```markdown
[Python](https://www.python.org/)
```

Фрагмент кода внутри строки заключается в обратные кавычки

```markdown
Команда `git status` показывает состояние репозитория
```

Многострочный код заключается между строками из трех обратных кавычек. После открывающих кавычек можно указать язык

````markdown
```python
print("Hello")
```
````

Таблица записывается с помощью символов `|` и строки-разделителя

```markdown
| Работа | Статус    |
| ------ | --------- |
| ЛР 1   | Выполнена |
```

Изображение добавляется конструкцией со знаком `!` перед ссылкой

```markdown
![Описание изображения](images/example.png)
```
